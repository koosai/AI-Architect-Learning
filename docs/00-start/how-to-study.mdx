# 学习方法

系统设计学习最容易失败的方式，是把自己困在“看了很多图，但从不自己画图”的状态。你需要把输入变成输出。

## 每周节奏

| 时间 | 动作 | 目的 |
|---|---|---|
| 2-3 小时 | 阅读章节和参考资料 | 建立术语和直觉 |
| 2-3 小时 | 跑代码或改实验 | 把概念落到行为 |
| 1-2 小时 | 画图 | 训练结构化表达 |
| 1 小时 | 录音讲解 | 暴露自己不清楚的地方 |
| 1 小时 | 复盘 | 写下 trade-off 和问题 |

## 讲解模板

每次练习都按这个顺序讲：

1. **Clarify requirements**：系统要解决什么问题，不解决什么问题。
2. **Estimate scale**：用户、请求、数据量、延迟目标。
3. **High-level design**：主要组件和数据流。
4. **Deep dive**：选择一个关键路径深入。
5. **Trade-offs**：速度、成本、一致性、复杂度、安全之间如何取舍。

## 初学者常见误区

- 把组件名字当答案：说“加 Redis”不等于解释缓存策略。
- 忽略失败路径：真实系统不是正常路径的集合，而是失败路径的集合。
- 只学 HLD 不写代码：LLD 和代码会暴露你对边界、状态和异常的理解。
- 只学 AI 不学系统：RAG、Agent、MCP、A2A 都仍然是分布式系统问题。

## 作品集标准

最终作品集不需要华丽，但必须有证据链：

- `architecture.md`：系统目标、约束、图、组件和数据流。
- `tradeoffs.md`：关键决策、备选方案和放弃理由。
- `runbook.md`：如何运行、测试、观测和排障。
- `labs/`：可运行代码。
- `evals/`：基础评测或 smoke tests。
