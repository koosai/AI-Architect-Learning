## 1. 设计初衷：企业 AI 落地的“合规与泄露”天堑

将大语言模型（LLM）引入企业办公（Word、Teams、PowerPoint）的商业价值是巨大的，但对系统架构提出了近乎苛刻的安全挑战：
1.  **数据越权泄露（Oversharing）**：如果员工 A 提问：“汇总公司当前的薪酬和财务计划”，而这些数据存放在员工 A 并没有权限查看的 SharePoint 文档里。如果 RAG 系统盲目检索并将其喂给 LLM 生成答案，就会造成极其严重的**企业越权信息泄露**。
2.  **租户隔离墙（Tenant Boundaries）**：企业客户最深切的担忧是“我的数据是否会被 Microsoft 拿去训练大模型”，从而导致商业机密在其他企业使用 AI 时泄露。
3.  **敏感标签（Sensitivity Labels）级联丢失**：企业文档通常打着“机密（Confidential）”、“内部公开”等 Sensitivity Labels。当 AI 提炼这些文档生成摘要并新建一个文档时，如果这个敏感标签丢失了，合规体系将瞬间失效。

为此，Microsoft 设计了结合 **Microsoft Graph 语义索引**、**Purview 敏感防护** 及 **安全修剪 RAG 环路** 的 Copilot 编排系统。

## 4. 核心机制拆解

### 4a. 语义索引构建管线 (Semantic Indexing Ingest)

为了让大模型具备在企业内部“博古通今”的检索精度，系统在后台对企业云盘与邮件进行持续的向量化提取：
1.  **文件监听与切片（Chunking）**：SharePoint / Exchange 监听到文档修改后，自动调用 Parser 将 Word/PPT/邮件 拆分成重叠的小文本块（每个 Chunk 约 200-500 字）。
2.  **向量嵌入（Vector Embeddings）**：调用 Embedding 模型，将每个文本块转化为固定维度的密集浮点向量。
3.  **权限列表绑定**：这是关键！对于每一个被索引的文件/Chunk，系统从 Active Directory 中实时提取其对应的 **ACL（Access Control List）**，记录哪些组（Groups）或用户具有只读/读写权限。将这些 ACL IDs 压缩后作为 metadata 与向量数据一起存入分布式向量数据库中。

```mermaid

    classDef store fill:#e8f5e9,stroke:#2e7d32,stroke-width:1.5px;

```

### 4b. 安全修剪与 Grounding 闭环 (Security Trimming & Grounding Loop)

安全修剪是防止企业内机密越权泄露的“安全网闸”：
*   **搜索阶段的安全剪裁（Read-time Security Trimming）**：
    1.  当用户 A 提问：“公司下一阶段的海外业务部署是什么”时，Orchestrator 接收请求，并并发向 Microsoft Graph 检索。
    2.  在检索向量库和搜索引擎时，系统强行在底层的 SQL/向量过滤条件中注入用户 A 自身的身份标识和其所属的所有 Active Directory Group IDs。
    3.  向量检索系统仅在**用户 A 拥有读取权限的文档子集**中执行余弦相似度计算，从物理底层直接丢弃无权查看的 Chunks。
*   **敏感标签级联继承（Purview Integration）**：
    1.  如果召回出的前 3 个安全 Chunks，分别来自两个打了 `机密 (Confidential)` 标签的文件和一个打了 `极密 (Highly Confidential)` 标签的文件。
    2.  LLM 生成摘要答案后，Microsoft Purview 策略引擎会评估这些上下文的源标签，并遵循 **“木桶效应 / 就高原则（Max Restriction Principle）”**，强行把最终返回的结果及新建的文件自动盖上 `极密 (Highly Confidential)` 的数字资产钢印，确保合规体系的完整闭环。

## 5. 关键数据结构与算法

### 5a. 余弦相似度 (Cosine Similarity) 向量检索

在 Semantic Index 中，文本块被转化为 $D$ 维稠密浮点向量。查询词 $q$ 与文本块 $d$ 的关联程度通过计算两个向量夹角的余弦值进行打分：

$$Similarity(q, d) = (q \cdot d) / (||q|| \cdot ||d||) = sum(q_i \cdot d_i) / (sqrt(sum(q_i^2)) \cdot sqrt(sum(d_i^2)))$$

#### 工程落地优化：
在超大企业租户尺度下，如果逐行计算余弦相似度，I/O 耗时将无法承受。因此，Semantic Index 预先对向量进行 **$L_2$ 范数归一化（Normalize）**，使得 ||q|| = ||d|| = 1。
这样，余弦相似度退化为**向量点积（Dot Product）**：
$$Similarity(q, d) = sum(q_i \cdot d_i)$$
点积计算仅包含简单的乘加操作（FMA），能够通过 GPU/CPU 的 AVX-512 向量化指令集得到数百倍加速，实现了亚毫秒级的检索。

---

### 5b. 动态安全修剪 ACL 剪裁位图 (Security Trimming Bitmap)

为了加速每次查询时的权限校验，Active Directory 采用**布隆过滤器（Bloom Filter）** 或 **压缩位图（Roaring Bitmaps）** 记录文档和用户的 SID。
对于每一个召回的候选 Chunk，其元数据保存一个 ACL Roaring Bitmap：`document_acl`。
当用户 A 查询时，获取用户自身的群组 SID 组成的 Roaring Bitmap：`user_sids`。
系统通过极速的**位图求交（Bitwise AND）**运算：
$$HasAccess = (document\_acl \cap user\_sids) \neq \emptyset$$
如果交集不为空，说明用户拥有访问该 Chunk 的权限，反之则无权查看。这在大规模高并发检索下，比传统的数据库嵌套 `IN (groups)` 联查性能提升了 3 个数量级。

## 9. 如果是你来设计：带权限安全修剪的 Grounding 编排器

### 场景设想
在企业级 RAG 系统中，当用户 A 发起 Prompt 提问时，Orchestrator 编排器需要进行 Grounding：
*   **语义检索**：从向量数据库中召回 Top K 相似的 Chunks。每个 Chunk 都有一个元数据结构记录了授权的 ACL Groups（如：`"acl_groups": ["HR", "Finance"]`）。
*   **权限过滤**：Orchestrator 从 Active Directory 获取用户 A 所属的群组列表（如：`["Engineering", "Design"]`）。
*   **安全修剪**：物理过滤掉那些用户 A 不具有对应 Group 权限的 Chunks，并最终将安全 Chunks 拼装成 Metaprompt。
