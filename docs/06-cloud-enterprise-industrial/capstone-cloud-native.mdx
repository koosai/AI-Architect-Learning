## 一、从“设计好的服务”到“生产里活着的服务”

M5 你设计了短链/高可用服务（负载均衡 + 限流 + 熔断 + 复制 + SLO）。现在要回答："它怎么真正跑起来、发出去、看得见、能演进？" 缺了交付链，再好的设计也只是 PPT。本课把 Month 6 所学组装成一条完整的交付流水线。

### 基础：打包与部署

- **容器化（[M6L1](./containers)）**：服务打成不可变镜像，依赖随镜像走，分层优化构建。
- **K8s 部署（[M6L2/L3](./kubernetes-basics)）**：用 Deployment 声明副本数（调和自愈）、Service 提供稳定入口、ConfigMap/Secret 注入配置、liveness/readiness 探针保证健康与零停机。

### 进阶：环境与发布自动化

- **IaC（[M6L5](./infrastructure-as-code)）**：用代码声明集群、数据库、网络——一条命令建出和生产一致的环境，可复制可回滚。
- **CI/CD（[M6L6](./cicd-pipelines)）**：提交 → 构建镜像 → 测试/安全门禁 → 一次构建逐级晋级 → [金丝雀发布（M6L4）](./autoscaling-rollout) + 失败自动回滚。

#### 金丝雀发布流量分配与自动回退决策流转

### 深入（选学）：看得见、治得住、可演进

- **可观测（[M6L7](./observability-advanced)）**：RED/USE 指标 + 结构化日志 + 链路追踪 + 基于 [SLO 燃尽率](./observability-advanced) 的告警——出问题分钟级定位。
- **服务网格（[M6L8](./service-mesh)，可选）**：服务多了，把 mTLS/重试/熔断/遥测下沉到 sidecar，统一治理。
- **一条主线贯穿全月**：[声明式 + <GlossaryTerm term="Reconciliation Loop" definition="调和循环 (Reconciliation Loop)：一种在控制系统和云原生引擎中广泛应用的控制回路算法。它不断观察系统的当前实际状态（Actual State），与声明的期望状态（Desired State）进行比较，如果发现不一致，则触发纠偏或变更操作，最终逼近期望状态。">调和</GlossaryTerm>（M6L2/L5）](./kubernetes-basics)——K8s 声明副本、IaC 声明资源、<GlossaryTerm term="GitOps" definition="GitOps：一种持续交付软件的运作模型。它将 Git 仓库作为基础设施与应用部署声明（Desired State）的唯一事实来源，并通过自动化的同步引擎（如 ArgoCD）监测运行环境（Actual State），当两者发生漂移时自动进行调和逼近。">GitOps</GlossaryTerm> 声明环境，全是"声明期望、自动逼近"。理解它，整条交付链就是一个统一心智模型，而非一堆零散工具。

  code={`# 把 Month 6 各环节串成一条端到端交付流水线（简化模拟）
def build_image(ctx):
    return (True, "image app:%s" % ctx["sha"])

def run_tests(ctx):
    return (ctx["tests_pass"], "tests")

def provision_infra(ctx):
    # IaC: 声明期望资源，幂等 apply（已存在则不重建）
    desired = {"cluster", "db", "lb"}
    ctx["infra"] = ctx.get("infra", set()) | desired
    return (True, "infra ready: %s" % sorted(ctx["infra"]))

def deploy_k8s(ctx):
    # K8s 调和：维持期望副本数
    ctx["replicas"] = ctx["desired_replicas"]
    return (True, "%d replicas running" % ctx["replicas"])

def canary_and_verify(ctx):
    # 金丝雀: 小流量验证 SLO，达标才放大，否则回滚
    if ctx["canary_error_rate"] > 0.01:
        return (False, "金丝雀指标恶化 -> 自动回滚")
    return (True, "金丝雀通过 -> 全量发布")

PIPELINE = [build_image, run_tests, provision_infra, deploy_k8s, canary_and_verify]

def deliver(ctx):
    for stage in PIPELINE:
        ok, msg = stage(ctx)
        print(("  ✓" if ok else "  ✗"), stage.__name__, "->", msg)
        if not ok:
            return "交付中止（已回滚）"
    return "端到端交付成功"

print("== 正常发布 ==")
print(deliver({"sha": "a1", "tests_pass": True, "desired_replicas": 3, "canary_error_rate": 0.001}))
print("== 金丝雀指标恶化 ==")
print(deliver({"sha": "b2", "tests_pass": True, "desired_replicas": 3, "canary_error_rate": 0.05}))`}

### 2. 整条链只有一条主线：声明式 + 调和

回看整个 Month 6：[容器](./containers)（不可变、声明镜像内容）、[K8s](./kubernetes-basics)（声明副本/配置，调和维持）、[IaC](./infrastructure-as-code)（声明资源，plan/apply 调和）、GitOps（Git 声明环境，自动同步）——**全部是基于 <GlossaryTerm term="Declarative API" definition="声明式 API (Declarative API)：指用户通过代码描述系统应该达到的‘期望状态（Desired State）’而不是执行的‘操作过程’，由后台控制器或引擎进行调和收敛。">声明式 API</GlossaryTerm> 来表达你期望的最终状态，让系统持续、幂等地逼近它**。一旦你用这个统一心智模型看待运维，从一个容器到整个生产环境都通了。这也是它和 [M4L1 封装变化](../design-patterns-lld/change-driven-design)、[M5 自愈](../core-components/service-discovery) 一脉相承的深层原因：**声明意图、隐藏过程、让系统自我维持。**

### 3. 真实案例：交付能力本身就是竞争力

DORA 多年研究证明：交付效能（部署频率、前置时间、变更失败率、恢复时间）高的组织，业务表现也更好。原因很直接——**能安全地一天发几十次，就能更快试验、更快响应市场、更快修复**。本月这套云原生交付链，正是把"交付"从拖后腿的瓶颈变成竞争优势的工程基础。对 AI Architect 尤其重要：AI 系统迭代快、模型/prompt/数据频繁变更（[Month 7-11](../llm-systems/overview)），没有可靠的交付链，AI 系统根本无法安全地快速演进。

## 常见误解

- **"架构师只要在 PPT 里把高可用、熔断、多副本复制的设计图画好就行了，具体的部署、环境搭建和流水线配置那是运维与 SRE 的琐碎事情"**：这是典型的“设计与交付割裂”误区。在现代云原生架构中，交付链的效能直接决定了系统架构的演进上限。如果环境不能通过 IaC 幂等且一致地建出来，如果应用镜像是手动拼凑而非标准化分层构建，如果发布流程依赖人肉操作且无可观测 SLO 监控兜底，那么再完美的高可用设计也会在频繁的生产变更中因“人为因素”彻底崩溃。**交付能力与稳定性是不可分割的整体，是架构师的首要职责之一。**
- **"我们的服务已经打成 Docker 镜像，并且成功部署在 Kubernetes 集群中了，我们已经实现了彻底的云原生化"**：大错特错。Kubernetes 仅仅是解决了容器的运行时编排和调和自愈，它只是云原生大版图中的冰山一角。如果底层云资源（如数据库、SLB、安全组）依然靠运维人肉在控制台点击创建（缺乏 IaC），如果代码发布依然通过 Jenkins 粗暴执行 shell 脚本（缺乏声明式 GitOps 与金丝雀网关），如果系统故障了依然靠人肉看日志而非 SLO 燃尽率告警（缺乏可观测），那这只是把“传统虚拟机应用强行套了个容器壳”，根本没有享受到云原生的弹性、一致性与自愈红利。
- **"频繁发布一定会降低系统的稳定性，为了保证高可用，成熟组织应当减少部署频率（如从每日发布改为每季度大版本发布）"**：这是被 DORA 科学调查彻底推翻的陈旧思维。大版本、低频的手动“大片式部署（Big Bang Deployment）”因为堆积了数月的大量变更，其单次发布的破坏半径极大，且由于各模块变更互相耦合，故障定位极其困难。相反，小步快跑的高频自动化交付，单次变更范围极其微小，且能够通过全自动的金丝雀验证与指标监控在毫秒级触发自动回滚，其**系统稳定性和变更失败率指标显著优于低频大版本发布**。
