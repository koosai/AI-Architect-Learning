:::tip 这个月的主题：从“一个服务”到“一群服务协作还不出事”
前四个月你会写干净的单个服务了。但真实系统是**一群服务在不可靠的网络上协作**：机器会挂、网络会断、流量会突增、数据要分布在多台机器上。这个月教你这群服务赖以生存的核心构件——负载均衡、网关、限流、熔断、复制、分片、共识。
:::

## 为什么需要这些构件

[M2L7 你学过水平扩展](../system-design-bridge/scaling-strategies)、[M2L11 学过容错](../system-design-bridge/reliability-fault-tolerance)的思想。这个月把它们落成**具体的、可设计的构件**：

- 加了 10 台机器，流量怎么均匀分到它们上？→ **负载均衡**
- 客户端怎么知道有哪些服务、它们在哪？→ **服务发现**
- 一个依赖变慢，怎么不让它拖垮整条调用链？→ **限流 / 熔断 / 隔离**
- 数据放一台机器扛不住，怎么分到多台还能查？→ **分区 / 分片**
- 一台数据库挂了，怎么不丢数据、不停服务？→ **复制 / 共识**

每一个都是"单机思维"到"分布式思维"的一次跃迁。

## 月末产出

一套"分布式构件"的可跑实现（一致性哈希负载均衡、令牌桶限流、熔断器、主从复制 + 读写仲裁、Raft 领导者选举），以及"给定一个服务，能设计出它的扩展 + 可靠性方案并量化取舍"的能力。

## 学习建议

- 每个构件先问："不用它会怎样崩？" 痛点想清楚，构件的设计自然成立。
- 始终带着[量化直觉](../foundations/performance-and-latency)：复制几份、分几片、限流到多少、超时设多久——架构师要会算。
- 多回 [M2L6 CAP](../system-design-bridge/cap-consistency)、[M2L11 容错](../system-design-bridge/reliability-fault-tolerance)：这个月是它们的工程落地。
