:::tip 多个 Agent 跑起来后，最大的麻烦不是智能，是运维
你把专精分工、编排、辩论、协议都搭好了——然后上线，麻烦来了：账单翻了 5 倍（[M10L1 早就警告](./why-multi-agent)）；某次输出错了，但你不知道是 10 个 Agent 里哪一个、哪一步坏的；一个 Agent 返回了垃圾，下游全被它带歪。**多 Agent 的运维难度是单 Agent 的好几倍**——更多组件、更多交互、更长链路。可观测、成本控制、错误隔离，一个都不能少，否则系统强大但没法运营。
:::

## 一、出了问题，不知道是哪一步坏的

单 Agent 出错你还能看它那一条轨迹；多 Agent 一出问题，排查是噩梦：
- **不知道哪坏的**：10 个 Agent、几十步交互，最终输出错了，到底哪个 Agent、哪一步出的问题？
- **成本失控**：每个 Agent 多轮调用，N 个 Agent = 成本翻几倍，账单吓人却说不清钱花哪了（[呼应 M10L1](./why-multi-agent)）。
- **错误传染**：一个 Agent 输出了错误/垃圾，下游 Agent 拿它当输入，错误被放大、污染全链（[呼应 M10L4 不可信数据隔离](./communication-state)）。

这些都不是"模型不够聪明"的问题，而是**工程和运维**的问题——多 Agent 把单 Agent 的每个运维难点都乘了好几倍。

## 二、三个核心概念（分层）

### 基础：分布式追踪——看清每一步

<GlossaryTerm term="Distributed Tracing (Multi-Agent)" definition="多 Agent 分布式追踪：用统一的 trace id 串起一次任务里所有 Agent 的每一步调用（谁、做了什么、输入输出、耗时、花了多少 token），形成可视的完整链路，便于定位是哪个 Agent 哪一步出了问题。">分布式追踪（tracing）</GlossaryTerm>：用一个统一的 trace id，把一次任务里**所有 Agent 的每一步**都记录并串起来——谁、做了什么、输入输出、耗时、花了多少 token。出问题时能一眼看到是哪个 Agent 哪一步坏的。这就是 [M1L11 可观测](../foundations/observability)、[M6L7 分布式追踪](../cloud-enterprise-industrial/observability-advanced) 在多 Agent 的直接应用——**多 Agent 就是一个分布式系统，可观测的老办法全适用**。没有追踪，多 Agent 就是个黑盒，根本没法运营。

### 进阶：成本归因与预算控制

- <GlossaryTerm term="Cost Attribution" definition="成本归因：把多 Agent 系统的总 token/调用成本拆解到每个 Agent、每一步，看清钱花在哪、哪个 Agent 最贵、是否值得，便于优化。">成本归因（cost attribution）</GlossaryTerm>：把总成本拆到每个 Agent、每一步——看清哪个 Agent 最烧钱、是否值得，才能优化（[呼应 M7L5 成本、M9L4 预算](../llm-systems/llm-api-cost-latency)）。
- **全局预算**：给整个多 Agent 任务设总预算上限（总 token/总调用/总时间），超了就停——单个 Agent 的[停止条件（M9L4）](../agent-architectures/stopping-budget) 不够，多 Agent 要**全局**预算，否则几个 Agent 各自不超、合起来爆炸。
- **降本手段**：贵的 Agent 用强模型、便宜的用小模型（[M7L5 路由](../llm-systems/llm-api-cost-latency)）；能用单 Agent 的别用多 Agent（[M10L1 克制](./why-multi-agent)）；缓存可复用的中间结果（[M7L8 缓存](../llm-systems/llm-api-cost-latency)）。

### 深入（选学）：错误隔离与传染防控

- <GlossaryTerm term="Error Propagation / Isolation" definition="错误传播与隔离：在多 Agent 链路中，一个 Agent 的错误输出会被下游当输入而放大污染全链。隔离手段包括校验每个 Agent 的输出、不让坏数据流入下游、单个 Agent 失败不拖垮整体。">错误传播与隔离</GlossaryTerm>：多 Agent 里错误会沿链路放大——A 错了，B、C 拿 A 的输出当真，错误被层层放大。必须**隔离**：校验每个 Agent 的输出（schema/合理性）再传给下游（[呼应 M10L4 schema 校验、verified 隔离](./communication-state)）、一个 Agent 失败不拖垮整体。这是 [M5 舱壁隔离（bulkhead）、断路器（circuit breaker）](../core-components/bulkhead-isolation) 在多 Agent 的对应——**故障隔离的老模式直接迁移**。
- **故障模式更多**：多 Agent 有单 Agent 没有的故障——死锁（互相等）、活锁（反复交接不前进）、级联失败（一个挂全挂）、协调者单点（[M10L3 Supervisor 是单点](./supervisor-orchestration)）。这些全是[分布式系统的经典故障（M2L11 容错）](../system-design-bridge/reliability-fault-tolerance)，不是新东西。
- **降级与兜底**：某个专精 Agent 挂了，整个系统能不能降级运行（少一个能力但不全停）？要设计[优雅降级（M5 弹性）](../core-components/circuit-breaker)——比如 critic Agent 挂了就跳过审查但记录告警，而非整个任务失败。
- **运维难度是核心成本**：[M10L1](./why-multi-agent) 说多 Agent "成本和混乱翻倍"，这一课就是那句话的兑现——**多 Agent 真正的长期成本，往往不是 token，而是运维复杂度**：更难调试、更难监控、更难保证可靠。架构师评估"要不要上多 Agent"时，必须把这份运维负担算进去。能用单 Agent 达标就别上多 Agent，不是因为多 Agent 不强，而是因为它的运维代价很实在。

## 三、跟我做一遍：追踪 + 全局预算 + 错误隔离

<PyRunner
  rows={44}
  expect="可追踪、控预算、隔离错误"
  code={`class Trace:
    def __init__(self, budget):
        self.steps = []
        self.budget = budget          # 全局预算(总 token)
        self.spent = 0
    def record(self, agent, action, tokens, ok):
        self.spent += tokens
        self.steps.append({"agent": agent, "action": action,
                           "tokens": tokens, "ok": ok})
    def over_budget(self):
        return self.spent > self.budget
    def cost_by_agent(self):          # 成本归因
        agg = {}
        for s in self.steps:
            agg[s["agent"]] = agg.get(s["agent"], 0) + s["tokens"]
        return agg

def validate(output):                 # 错误隔离:校验后才传下游
    return isinstance(output, dict) and output.get("ok") is True

def run_pipeline(agents, trace):
    data = {"ok": True, "val": "start"}
    for name, fn, cost in agents:
        if trace.over_budget():        # 全局预算:超了就停
            trace.record(name, "SKIPPED_budget", 0, False)
            break
        out = fn(data)
        ok = validate(out)             # 隔离:坏输出不往下传
        trace.record(name, "run", cost, ok)
        if not ok:
            trace.record(name, "ISOLATED_bad_output", 0, False)
            break                      # 不让错误污染下游
        data = out
    return data

agents = [
    ("researcher", lambda d: {"ok": True, "val": "facts"}, 100),
    ("analyst",    lambda d: {"ok": False, "val": "garbage"}, 200),  # 坏输出
    ("writer",     lambda d: {"ok": True, "val": "report"}, 150),    # 不该被执行
]
t = Trace(budget=1000)
run_pipeline(agents, t)
for s in t.steps: print(s)
print("成本归因:", t.cost_by_agent())
print("可追踪、控预算、隔离错误")`}
/>

每一步都被追踪（谁、花了多少、成功否），analyst 输出了坏数据就被隔离、不传给 writer（防污染），成本能归因到每个 Agent，还有全局预算兜底。这就是多 Agent 运维的三大支柱在一段代码里的缩影。**试试**：把 budget 改成 250，看预算如何提前截停；把 analyst 改成正常输出，看链路正常走完——体会"校验后才传下游"如何挡住错误传染。

### 2. 多 Agent 就是分布式系统——你的旧地图全能用

这一课每一个"新"难题，都是分布式系统的老朋友：追踪每个 Agent = [分布式追踪（M6L7）](../cloud-enterprise-industrial/observability-advanced)；一个 Agent 坏不拖垮全链 = [舱壁隔离/断路器（M5）](../core-components/bulkhead-isolation)；协调者单点 = [单点故障（M2L11）](../system-design-bridge/reliability-fault-tolerance)；死锁活锁级联 = 分布式系统经典故障；全局预算 = [限流/配额（M5L5）](../core-components/rate-limiting)；优雅降级 = [弹性设计（M5）](../core-components/circuit-breaker)。**这意味着你不需要为"多 Agent 运维"重新学一套——你十几节课积累的分布式系统运维直觉，整体迁移过来就是。** 反过来说，一个没有分布式系统运维基础的人去搭生产多 Agent，会在这些早被解决过的坑里反复摔——这正是为什么本书坚持先打牢系统设计地基（Month 1-6）再上 AI（Month 7-12）：**AI 系统的可靠性，绝大部分来自传统软件工程，而非模型本身。** 多 Agent 运维是这句话最浓缩的体现。

### 3. 真实案例：多 Agent 成本与可靠性的双重失控，与它的代价

多 Agent 系统在生产中最常见的两类翻车，都不是"模型不够聪明"：(1) **成本失控**——上线后账单是预估的好几倍，因为没人把成本归因到每个 Agent、没设全局预算，几个 Agent 各自多跑几轮，合起来 token 爆炸，最后发现某个"以防万一"加的审查 Agent 贡献了 40% 成本却几乎没拦住过错误（该砍）；(2) **可靠性失控**——某个上游 Agent 偶尔返回畸形输出，没有校验隔离，下游全被污染，最终用户看到离谱结果，排查时因为没有 trace 花了几天才定位到是哪个 Agent。这两类问题的共同根源是**把多 Agent 当"更强的单 Agent"来上线，而没把它当分布式系统来运维**。教训呼应全课主线：[M10L1](./why-multi-agent) 的"成本和混乱翻倍"不是吓唬，是真实账单和真实事故；多 Agent 的能力上限很高，但能不能把这份能力**稳定、可控、可负担**地交付，取决于你愿不愿意付出分布式系统级别的运维工程。**这也是区分"能跑个 demo"和"能上生产"的分水岭。**

- 一个 Agent 返回垃圾，下游会被污染吗？有输出校验和故障降级吗？这些运维成本你算进决策了吗？

## 常见误解

- **"多 Agent 主要难在让它们更聪明"**：难点是运维（可观测/成本/错误隔离），不是智能。
- **"每个 Agent 各自有停止条件就够了"**：要全局预算，否则各自不超、合起来爆炸。
- **"多 Agent 运维要重新学一套"**：它就是分布式系统运维，旧地图全能用。
