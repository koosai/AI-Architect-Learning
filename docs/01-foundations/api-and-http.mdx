## 一、浏览器是怎么和你的后端说话的？

你点一下网页上的"报名"，背后发生的是：浏览器把一个 <GlossaryTerm term="HTTP Request" definition="HTTP 请求：客户端发给服务器的一条消息，包含方法（GET/POST…）、路径（/signups）、头（headers）和可选的正文（body）。">HTTP 请求</GlossaryTerm> 发到你的服务器，服务器处理后回一个 <GlossaryTerm term="HTTP Response" definition="HTTP 响应：服务器回给客户端的消息，包含状态码（200/404…）、头和正文。">HTTP 响应</GlossaryTerm>。这套"一问一答"就是 <GlossaryTerm term="Client-Server" definition="客户端-服务器模型：客户端发起请求，服务器提供响应。Web 的基本交互结构。">客户端-服务器</GlossaryTerm> 模型。

一个 API 就是你的服务器对外公开的一组"可以这样问我"的约定。它要约定四件事：**用什么方法、访问什么路径、传什么 body、回什么状态码**。

## 二、三个核心概念（分层）

### 基础：HTTP 方法与状态码

<GlossaryTerm term="HTTP Method" definition="表示操作意图的动词：GET 读取、POST 创建、PUT 替换、PATCH 局部更新、DELETE 删除。">HTTP 方法</GlossaryTerm> 表达"你想干什么"：

| 方法 | 意图 | 幂等吗（回扣 L6） |
|---|---|---|
| GET | 读取 | ✅ |
| POST | 创建 | ❌ |
| PUT | 整体替换 | ✅ |
| DELETE | 删除 | ✅ |

<GlossaryTerm term="HTTP Status Code" definition="三位数字表示结果类别：2xx 成功，3xx 重定向，4xx 客户端错误（你传错了），5xx 服务端错误（我出错了）。">状态码</GlossaryTerm> 表达"结果如何"——这正是 [L4 错误分类](./error-handling) 的落地：

- **2xx**：成功（200 OK、201 Created）。
- **4xx**：客户端的锅（400 参数错、401 未认证、404 找不到、409 冲突）。
- **5xx**：服务端的锅（500 内部错、503 不可用）。

### 进阶：REST——把一切看成"资源"

<GlossaryTerm term="REST" definition="一种 API 设计风格：把系统建模成资源（名词，如 /signups），用 HTTP 方法（动词）操作它们，无状态、用状态码表达结果。">REST</GlossaryTerm> 的核心思想：**用名词表示资源（`/signups`、`/signups/42`），用 HTTP 方法表示动作**，而不是把动词塞进路径（别设计 `/createSignup`）。再配合 [L5 的无状态](./state-and-storage) 和 [L6 的方法幂等语义](./idempotency)，就得到一套清晰、可缓存、可扩展的接口。

### 深入（选学）：REST 不是唯一答案

REST 之外还有 <GlossaryTerm term="gRPC" definition="基于 HTTP/2 和 Protobuf 的高性能 RPC 框架，强类型、二进制、支持流式，常用于服务间内部通信。">gRPC</GlossaryTerm>（服务间高性能调用）和 <GlossaryTerm term="GraphQL" definition="一种查询语言，客户端用单个请求精确指定要哪些字段，避免一次返回过多或过少（over/under-fetching）。">GraphQL</GlossaryTerm>（客户端自定义要哪些字段）。它们解决 REST 的不同痛点，下面深潜会对比。

## 三、跟我做一遍：一个最小 HTTP 路由器

<PyRunner
  expect="201"
  code={`# 一个极简的 HTTP 服务：用 (方法, 路径) 找到处理函数，返回 (状态码, 响应体)
app = {"signups": {}, "next_id": 1}

def handle(method, path, body=None):
    if path == "/signups" and method == "POST":
        if not body or "email" not in body:
            return 400, {"error": "email_required"}       # 客户端错误
        sid = app["next_id"]; app["next_id"] += 1
        app["signups"][sid] = {"id": sid, "email": body["email"]}
        return 201, app["signups"][sid]                    # 创建成功
    if path == "/signups" and method == "GET":
        return 200, list(app["signups"].values())          # 读取列表
    return 404, {"error": "not_found"}                      # 找不到

print(handle("POST", "/signups", {"email": "ada@x.com"}))  # 201 Created
print(handle("POST", "/signups", {}))                       # 400 缺 email
print(handle("GET", "/signups"))                            # 200 列表
print(handle("GET", "/unknown"))                            # 404`}
/>

注意每个返回都带了**正确的状态码**——这就是你的 API 契约的一部分。**试试**：加一个 `GET /signups/<id>` 路由，命中返回 200、找不到返回 404。

## 架构师深潜（Staff+ 视角）

### 1. API 是契约，改它要极其小心

一旦有客户端依赖你的 API，它的每个可见行为（字段名、状态码、甚至错误格式）都会被某人依赖——这正是 [L2 的 Hyrum 定律](./modules-and-contracts)。所以要做**向后兼容**的演进：加字段（安全）、不删不改已有字段（危险）、用版本号（`/v2/`）做破坏性变更。

### 3. 真实案例：API 网关是系统的前门

[ChatGPT 案例](../atlas/chatgpt.mdx) 和几乎所有大系统，请求第一站都是 API 网关：它在 HTTP 层做鉴权、限流、路由——把横切关注点从业务服务里抽出来（回扣 [L2 的关注点分离](./modules-and-contracts)）。你设计的每个 API，最终都活在这样一个网关后面。

## 常见误解

- **"接口随便返回个 200 就行"**：状态码是契约，客户端和中间件靠它判断。
- **"路径里写动词更直观"**：REST 用名词资源 + 方法动词，更一致、可缓存。
- **"API 上线后想改就改"**：有人依赖就不能随便改，要兼容或版本化。
