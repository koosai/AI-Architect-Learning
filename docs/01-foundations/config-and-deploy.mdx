:::tip 这一课终结"在我机器上是好的"
代码在你电脑跑得好，一上线就崩——十有八九是因为数据库地址、密钥、超时被写死在了代码里，换个环境就不对。把"会变的东西"从代码里拿出来，是工程化的第一步。
:::

## 一、为什么"在我机器上是好的"？

你的代码里写死了 `db_host = "localhost"`、`timeout = 5000`、甚至把数据库密码硬编码进去。在你电脑上当然好——可一旦部署到测试环境、生产环境，这些值全都不对，于是崩。而且密码进了代码 = 进了 Git 仓库 = 全公司可见的安全事故。

> 根因：**会随环境变化的东西（配置、密钥）不该和代码写在一起。** 这一课就讲怎么分开它们，以及怎么把新版本安全地发上线。

## 二、三个核心概念（分层）

### 基础：配置与代码分离

<GlossaryTerm term="Configuration" definition="配置：随部署环境变化的值（数据库地址、超时、密钥、开关）。应与代码分离，通常通过环境变量注入。">配置</GlossaryTerm> 是"会随环境变的值"。原则：**同一份构建产物（代码），靠外部注入的配置，在不同环境表现不同**。最常见的注入方式是<GlossaryTerm term="Environment Variable" definition="环境变量：操作系统层面注入给进程的键值对（如 DB_HOST）。是把配置从代码里分离出来的标准方式。">环境变量</GlossaryTerm>。

特别地，**密钥（secret）绝不能写进代码**，只能从环境/密钥管理服务注入。

### 进阶：环境隔离与一次构建多处部署

通常有多个<GlossaryTerm term="Environment" definition="环境：相互隔离的运行场景，典型是 dev（开发）、staging（预发）、prod（生产）。同一代码在不同环境用不同配置运行。">环境</GlossaryTerm>：dev / staging / prod，互相隔离。理想做法是<GlossaryTerm term="Build Once, Deploy Many" definition="一次构建、多处部署：构建出一个不可变的产物（如容器镜像），同一个产物部署到各环境，差异只来自注入的配置。避免“测试的和上线的不是同一个东西”。">一次构建、多处部署</GlossaryTerm>——构建一个不可变产物，到处部署，差异只来自配置。这样"测过的"和"上线的"是同一个东西。

### 深入（选学）：部署策略与回滚

把新版本送上线不是"覆盖一下"那么简单。常见策略：<GlossaryTerm term="Blue-Green Deployment" definition="蓝绿部署：准备两套环境（蓝=旧、绿=新），新版在绿上就绪后一次性切流量；出问题立刻切回蓝。">蓝绿</GlossaryTerm>、<GlossaryTerm term="Canary Deployment" definition="金丝雀部署：先把新版本放给一小部分流量（如 1%），观察指标正常再逐步放量；异常则回滚。">金丝雀</GlossaryTerm>、滚动。它们都依赖 [L5 的无状态](./state-and-storage)（实例可互换）。而第一原则是：**出问题时，回滚要比修复更快、更可靠。**

## 三、跟我做一遍：同一代码，不同环境

<PyRunner
  expect="prod 超时更短"
  code={`DEFAULTS = {"timeout_ms": 1000, "log_level": "info"}
PER_ENV = {
    "dev":  {"log_level": "debug"},
    "prod": {"timeout_ms": 500},
}

def load_config(env, env_vars=None):
    env_vars = env_vars or {}
    cfg = {**DEFAULTS, **PER_ENV.get(env, {})}      # 默认 < 环境特定
    if "TIMEOUT_MS" in env_vars:                     # 环境变量优先级最高
        cfg["timeout_ms"] = int(env_vars["TIMEOUT_MS"])
    return cfg

print("dev :", load_config("dev"))
print("prod:", load_config("prod"))
# 临时用环境变量覆盖（不改代码）
print("prod+override:", load_config("prod", {"TIMEOUT_MS": "200"}))
print("prod 超时更短" if load_config("prod")["timeout_ms"] < load_config("dev")["timeout_ms"] else "?")`}
/>

注意优先级：**默认值 < 环境特定 < 环境变量**。同一份代码，配置一变，行为就变——而且不用改、不用重新构建。**试试**：给 `prod` 加一个 `log_level: "warn"`，看它如何覆盖默认的 `info`。

## 架构师深潜（Staff+ 视角）

### 1. 回滚优先于修复

线上出事时，最快恢复的方式通常不是"赶紧改代码修"，而是**立刻回滚到上一个已知好版本**。所以每次部署都要保证"可一键回滚"——这要求新旧版本兼容（尤其数据库 schema 变更要向后兼容，回扣 [L9 契约演进](./api-and-http)）。

### 4. 真实案例：热升级与灰度

[WhatsApp 的 Erlang](../atlas/whatsapp.mdx) 支持热代码升级——不断连接就换代码。[ChatGPT](../atlas/chatgpt.mdx) 这类系统则靠金丝雀逐步放量新模型/新版本。**怎么安全地"换正在飞的飞机的引擎"，是大规模系统的日常。**

## 常见误解

- **"配置写代码里方便"**：换环境就崩、密钥泄露，是上线事故的常客。
- **"部署就是把文件传上去覆盖"**：没有灰度和回滚，一出错就是全员事故。
- **"少发布更稳"**：DORA 表明小步高频 + 可回滚反而更稳。
