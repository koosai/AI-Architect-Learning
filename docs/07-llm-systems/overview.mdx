:::tip 这个月的视角转变：LLM 不是“魔法大脑”，是“会出错的系统组件”
前六个月你学会了设计可靠的分布式系统。现在引入一个新组件——大语言模型。它很强，但也很特别：**输出不确定、会一本正经胡说、有上下文长度上限、按 token 收费、延迟高且波动大。** 这个月教你像架构师那样对待它：理解它的内部和约束，再用工程手段（提示、工具、缓存、评测、防护）把它驯服成一个可靠的系统组件。
:::

## 为什么要先理解 LLM 的内部

很多人把 LLM 当黑魔法，写不出可靠的 AI 系统。架构师的做法相反：**先理解它怎么工作，约束自然就清楚了。**

- 它**一个 token 一个 token 地预测下一个**生成 → 解释了延迟、流式输出、为什么会"越说越偏"。
- 它**没有真正的记忆，只能看到上下文窗口里的内容** → 解释了为什么要管理上下文、为什么需要 RAG（[Month 8](../rag/overview)）。
- 它**按 token 收费、上下文越长越慢越贵** → 解释了为什么要精简提示、缓存、选对模型档位。
- 它**是概率生成、不保证正确** → 解释了为什么必须评测、防护、结构化校验。

理解这些，你就不会把 LLM 当"许愿池"，而会把它当一个**有明确输入输出契约、有失败模式、需要工程包裹**的组件——这正是前六个月一直在训练的思维。

## 学习建议

- 始终带着前六个月的工程思维：LLM 是个组件，给它加[超时/重试/熔断/降级（M5）](../core-components/circuit-breaker)、[可观测（M6L7）](../cloud-enterprise-industrial/observability-advanced)、[评测门禁（M6L6）](../cloud-enterprise-industrial/cicd-pipelines)。
- 区分"模型能力"和"系统可靠性"：模型再强，没有评测、防护、缓存、成本控制，也做不出生产级 AI 产品。
- 选模型默认用最新、最强的 Claude 模型（如 Opus 4.8 `claude-opus-4-8`、Sonnet 4.6 `claude-sonnet-4-6`、Haiku 4.5 `claude-haiku-4-5-20251001`），再按成本/延迟需求向下选档。
